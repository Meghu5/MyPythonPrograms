Playwright Interview Preparation: 10 Real-World Scenario Questions and Answers
These are senior-level Playwright automation interview questions. For your interview preparation,
focus on three things for every scenario: the solution, the technical implementation, and why you
chose that approach.I'll use Playwright with Python and pytest for the code examples.
 The same concepts apply to Playwright with JavaScript/TypeScript, with syntax differences.

1. How would you automate a login flow that uses SSO, OTP, or MFA in Playwright?
Interview answer:
I would first understand the authentication mechanism and determine whether the objective is to
validate the complete authentication flow or test the application after authentication.
- SSO: Use a dedicated test identity and automate the identity provider when end-to-end authentication
testing is required.- OTP/MFA: Use an approved test-environment authentication mechanism, such as a
test OTP provider, identity-provider test policy, or test-only authentication hook.
- Session reuse: For most functional tests, authenticate once and reuse the Playwright storage state.
- Security: Never hardcode production credentials, bypass production MFA, or commit authentication
tokens to source control.

Example A: Reuse an authenticated session
# conftest.pyimport pytestfrom playwright.sync_api import sync_playwright

def browser_context():
with sync_playwright() as p:
   browser = p.chromium.launch(headless=True)
    context = browser.new_context( storage_state="auth_state.json"        )

Generate the state through an approved login setup script:
from playwright.sync_api import sync_playwrightwith sync_playwright() as p:    browser = p.chromium.launch(headless=True)    page = browser.new_page()    page.goto("https://test.example.com/login")    page.get_by_label("Username").fill("test-user")    page.get_by_label("Password").fill("test-password")    page.get_by_role("button", name="Sign in").click()    page.get_by_role("heading", name="Dashboard").wait_for()    page.context.storage_state(path="auth_state.json")    browser.close()



The credentials are illustrative; in a real framework, read them from environment variables or a secret manager.
Important: If authentication depends on an external identity provider, the setup script must complete the actual SSO/MFA flow before saving the state. The example assumes that login completes without additional interactive challenges.

Here, test_otp is supplied by an approved test fixture or authentication service.
Real-world example: In an airline booking application, I would reuse an authenticated test session for ordinary booking and check-in tests, but retain separate end-to-end tests that validate SSO, MFA challenges, invalid OTPs, and expired sessions.
Senior-level follow-up: Storage state may contain cookies and tokens. Protect it as a secret, exclude it from Git, and create isolated sessions when testing roles or permissions.

2. Your Playwright tests pass locally but fail in CI/CD. How would you investigate and fix this?
Interview answer:
I would not immediately add retries or increase every timeout. I would identify whether the failure is caused by the environment, synchronization, test data, browser dependencies, parallel execution, or application behavior.
My debugging sequence
1. Reproduce: Run the same browser, headless mode, test data, and command locally.
2. Inspect evidence: Review the stack trace, screenshot, trace, console output, and network failures.
3. Check the environment: Compare browser versions, Playwright versions, operating system, installed dependencies, secrets, and environment variables.
4. Check synchronization: Replace fixed sleeps with locator assertions and condition-based waits.
5. Check isolation: Look for shared accounts, reused records, race conditions, and tests that depend on execution order.
6. Fix and verify: Re-run the failed test repeatedly and then run the full suite in CI.

Code: Configure useful failure diagnostics
# playwright.config.py is used in JavaScript/TypeScript,# so for Python use pytest.ini and pytest command options.



For Python, enable tracing, screenshots, and video in your Playwright pytest configuration:
# pytest.ini
[pytest]
addopts = --tracing retain-on-failure --screenshot only-on-failure --video retain-on-failure


Run:
pytest -v --headed


Use --headed for local visual debugging when a display is available; CI normally runs headless.
To collect CI diagnostics, run:
pytest --tracing retain-on-failure \
       --screenshot only-on-failure \
       --video retain-on-failure


These options are provided by the Playwright pytest plugin. Open the resulting trace to inspect the action timeline, DOM snapshots, and network activity.
Common causes and fixes
Problem	Correct fix
Browser or OS mismatch	Install supported browser binaries and OS dependencies
Element not ready	Use locator auto-waiting and web-first assertions
Tests collide in parallel	Isolate accounts, records, and test data
API is slower in CI	Wait for the actual response or UI state
Missing secrets	Configure CI secret variables securely
Random failures	Use traces and repeated runs to identify the root cause
Real-world example: A booking test passes locally but fails in CI because the flight search results take longer to load. Instead of adding time.sleep(10), I would wait for the expected flight result or a loading indicator to disappear, then assert that the correct flight is visible.
Key interview point: Retries can help identify flaky tests, but they do not fix the underlying defect.
3. How do you handle dynamic elements when selectors keep changing frequently?
Interview answer:
I prefer stable, user-facing locators such as accessible roles, labels, and meaningful test IDs. I avoid brittle selectors based on generated CSS classes, absolute XPath, or DOM position.
My approach is:
1. Ask developers to provide stable data-testid attributes where necessary.
2. Use Playwright's role, label, and text locators.
3. Scope locators to a stable parent container.
4. Use explicit conditions and assertions rather than arbitrary waits.
5. If the application changes its DOM, update the locator based on the intended behavior.
Example A: Use a stable test ID
def test_add_to_cart(page):    page.goto("https://test.example.com/products")    page.get_by_test_id("product-card-101").get_by_role(        "button", name="Add to cart"    ).click()    assert page.get_by_test_id(        "cart-count"    ).inner_text() == "1"



Here, get_by_test_id() is appropriate when the application exposes stable test IDs.
Example B: Use a semantic locator
page.get_by_role(    "button",    name="Continue",    exact=True).click()



This is generally more robust than:
page.locator(    "div.container > div:nth-child(3) > button").click()



The second selector depends on the page's internal structure, which can change without changing the actual user workflow.
Real-world example: An airline website generates different CSS classes for its flight cards after each build. I would locate a flight card using a stable flight identifier or test ID, then locate the booking button inside that card.
Senior-level point: Playwright locators are designed to resolve elements at action time and support auto-waiting. Prefer a reliable locator over adding retries around a fragile selector.

4. If a page contains multiple elements with the same text, how do you interact with the correct one?
Interview answer:
I would scope the locator to a unique parent, use a more specific role or accessible name, and verify uniqueness when the element is expected to be unique. I would use .nth() only when the ordering itself is meaningful and stable.
Example A: Scope to a particular card
Suppose a page displays multiple flights, each with a Book now button.
flight_card = page.get_by_test_id("flight-AB123")book_button = flight_card.get_by_role(    "button",    name="Book now",    exact=True)assert book_button.count() == 1book_button.click()



This targets the button inside flight AB123, rather than the first Book now button on the page.
Example B: Select by index when appropriate
book_buttons = page.get_by_role(    "button",    name="Book now",    exact=True)assert book_buttons.count() == 3book_buttons.nth(1).click()



This selects the second button using zero-based indexing.
However, I would not use .nth(1) merely to silence a strict-mode error. If the second button represents a particular flight, I would rather identify that flight through a stable business identifier.
Example C: Filter by meaningful content
flight_card = page.locator(    "[data-testid='flight-card']").filter(has_text="AB123")flight_card.get_by_role(    "button",    name="Book now").click()



Real-world example: If three products have the same Add to cart button, scope the button to the product name or product ID. This prevents accidentally adding the wrong product.
Key interview point: Uniqueness should come from business meaning or page structure, not a guess about element order.

5. An API call succeeds, but the UI updates late, causing test failures. How would you handle synchronization?
Interview answer:
I would distinguish between the API response and the UI's rendering process. A successful HTTP response does not guarantee that the frontend has processed the response, updated its state, and rendered the expected element.
I would wait for the relevant response when needed, followed by a condition-based UI assertion. I would avoid fixed sleeps and use expect_response() only when I need to coordinate with the request itself.
Example A: Wait for the API response and then verify the UI
from playwright.sync_api import expectdef test_flight_search(page):    page.goto("https://test.example.com/flights")    page.get_by_label("Origin").fill("AUH")    page.get_by_label("Destination").fill("LHR")    with page.expect_response(        lambda response:            "/api/flights/search" in response.url            and response.request.method == "GET"    ) as response_info:        page.get_by_role(            "button", name="Search flights"        ).click()    response = response_info.value    assert response.status == 200    expect(        page.get_by_test_id("flight-results")    ).to_be_visible()    expect(        page.get_by_text("AB123", exact=True)    ).to_be_visible()



This checks both the API result and the rendered flight result.
Important: The URL pattern is illustrative. Match the actual endpoint and HTTP method used by the application.
Example B: When only the UI outcome matters
from playwright.sync_api import expectpage.get_by_role("button", name="Search flights").click()expect(    page.get_by_test_id("flight-results")).to_be_visible(timeout=10000)



This is often enough when Playwright's auto-waiting and the web-first assertion cover the requirement.
What I would avoid
import timetime.sleep(5)



A fixed sleep always waits for the specified duration, even if the page becomes ready earlier. It can also fail when the application takes longer than expected.
Real-world example: The booking API returns a reservation reference immediately, but the frontend displays the confirmation card after updating its state. I would assert the actual confirmation card and reservation reference, not merely the API status code.
Senior-level point: Do not blindly wait for networkidle on applications with polling, analytics, or persistent network connections. Wait for the specific business condition instead.

6. How would you implement and validate file upload and file download functionality using Playwright?
Interview answer:
For uploads, I would use Playwright's file-input APIs or file chooser event handling. For downloads, I would capture the download event, save the file, and validate the filename, existence, and contents. I would also test negative cases such as unsupported file types and file-size limits.
Example A: File upload
from pathlib import Pathfrom playwright.sync_api import expectdef test_upload_document(page):    page.goto("https://test.example.com/documents")    file_path = Path("tests/data/passport.pdf")    assert file_path.exists()    page.get_by_label("Upload document").set_input_files(        str(file_path)    )    expect(        page.get_by_text("passport.pdf")    ).to_be_visible()    page.get_by_role(        "button", name="Submit"    ).click()    expect(        page.get_by_text("Upload successful")    ).to_be_visible()



This assumes the file input has an accessible label and the application shows a success message.
Example B: File upload using a file chooser
Use this approach when clicking a button opens the operating system's file picker.
def test_upload_via_file_chooser(page):    page.goto("https://test.example.com/documents")    with page.expect_file_chooser() as chooser_info:        page.get_by_role(            "button", name="Choose file"        ).click()    chooser = chooser_info.value    chooser.set_files("tests/data/passport.pdf")



Example C: File download and validation
from pathlib import Pathdef test_download_report(page, tmp_path):    page.goto("https://test.example.com/reports")    with page.expect_download() as download_info:        page.get_by_role(            "link", name="Download report"        ).click()    download = download_info.value    assert download.suggested_filename == "report.csv"    saved_file = tmp_path / download.suggested_filename    download.save_as(saved_file)    assert saved_file.exists()    assert saved_file.stat().st_size > 0    content = saved_file.read_text(encoding="utf-8")    assert "booking_id" in content



The example assumes a UTF-8 CSV report with a booking_id header. For PDFs, binary files, or other formats, I would use the appropriate parser or validation method.
Real-world example: An airline customer uploads a passport scan during online check-in. I would test valid PDF/JPEG uploads, unsupported formats, oversized files, server rejection, and the correct association of the uploaded document with the passenger.
For downloads, I would validate not only that a file was downloaded but also that its contents correspond to the selected booking or report.
Senior-level point: Use pytest's tmp_path fixture to isolate generated files and avoid test collisions.

7. How would you design your Playwright tests to run across multiple browsers and devices?
Interview answer:
I would design a browser-independent test suite using reusable page objects, shared test data, and isolated browser contexts. I would configure separate execution profiles for Chromium, Firefox, WebKit, desktop viewports, and mobile device emulation.
I would also distinguish between browser coverage and real-device coverage: mobile emulation tests viewport, touch behavior, and certain device settings, but it does not replace testing on physical devices.
Example A: Cross-browser testing with Python and pytest
# conftest.pyimport pytestfrom playwright.sync_api import sync_playwright@pytest.fixture(params=["chromium", "firefox", "webkit"])def page(request):    with sync_playwright() as p:        browser_type = getattr(p, request.param)        browser = browser_type.launch(headless=True)        context = browser.new_context(            viewport={"width": 1365, "height": 768}        )        page = context.new_page()        yield page        context.close()        browser.close()



Every test using this fixture runs against all three configured browser engines.
Install the supported browser binaries before execution:
playwright install


On Linux CI environments, install required operating-system dependencies as well:
playwright install --with-deps


Example B: Mobile emulation
import pytestfrom playwright.sync_api import sync_playwright@pytest.fixturedef mobile_page():    with sync_playwright() as p:        iphone = p.devices["iPhone 13"]        browser = p.chromium.launch(headless=True)        context = browser.new_context(**iphone)        page = context.new_page()        yield page        context.close()        browser.close()



Use mobile_page in a test to exercise the mobile layout.
How I would organize the test strategy
Test category	Execution strategy
Critical smoke tests	All supported browser engines
Full regression	Parallel execution across selected browsers
Responsive UI	Desktop, tablet, and mobile viewports
Mobile-specific behavior	Device emulation plus real-device tests where needed
Accessibility	Automated checks and targeted manual validation
Real-world example: In an airline booking portal, I would validate flight search and booking confirmation across Chromium, Firefox, and WebKit. I would additionally verify that the mobile booking flow works at a small viewport and that passenger details remain usable on touch-enabled screens.
Senior-level point: Run tests in parallel only when their data and accounts are isolated. A cross-browser test suite is not reliable if different workers modify the same booking.

8. If the backend is unstable, how would you mock or intercept API responses in Playwright?
Interview answer:
I would intercept the relevant API request and return a controlled response. This allows UI tests to remain deterministic while the backend is unstable or while I need to test scenarios that are difficult to reproduce.
I would use mocks for frontend behavior and error-state coverage, but keep separate integration and end-to-end tests against the real backend.
Example A: Mock a successful flight search
def test_flight_search_with_mock(page):    def mock_flights(route):        route.fulfill(            status=200,            content_type="application/json",            json={                "flights": [                    {                        "flightNumber": "AB123",                        "price": 1200,                        "currency": "AED"                    }                ]            }        )    page.route("**/api/flights/search", mock_flights)    page.goto("https://test.example.com/flights")    page.get_by_role(        "button", name="Search flights"    ).click()    assert page.get_by_text(        "AB123", exact=True    ).is_visible()    assert page.get_by_text(        "AED 1200", exact=True    ).is_visible()



The response schema and displayed price are illustrative and should match the actual application.
Example B: Mock a server error
def test_flight_search_server_error(page):    page.route(        "**/api/flights/search",        lambda route: route.fulfill(            status=500,            content_type="application/json",            json={"message": "Internal server error"}        )    )    page.goto("https://test.example.com/flights")    page.get_by_role(        "button", name="Search flights"    ).click()    assert page.get_by_text(        "Unable to load flights"    ).is_visible()



Example C: Simulate a network failure
def test_network_failure(page):    page.route(        "**/api/flights/search",        lambda route: route.abort()    )    page.goto("https://test.example.com/flights")    page.get_by_role(        "button", name="Search flights"    ).click()    assert page.get_by_text(        "Something went wrong"    ).is_visible()



Which scenarios would I mock?
- Successful responses with known data.
- Empty search results.
- HTTP 400 validation errors.
- HTTP 401 or 403 authentication and authorization failures.
- HTTP 500 server errors.
- Network timeouts and aborted requests.
- Delayed responses and loading indicators.
Real-world example: The flight-pricing service is intermittently unavailable. I can still test that the frontend displays an error message, offers a retry action, and does not show stale prices by mocking the relevant response.
Senior-level point: A mock can hide backend defects if it is used for every test. I would retain a smaller set of real API and end-to-end tests to validate actual contracts and integrations.

9. How would you capture and assert console errors or failed network calls during test execution?
Interview answer:
I would register event listeners before performing the action under test. I would capture JavaScript console errors, uncaught page errors, and failed requests. Where appropriate, I would also inspect HTTP responses for server errors.
I would distinguish between a network request that failed to reach the server and a request that reached the server but returned an HTTP error.
Example: Capture and assert browser errors
def test_page_has_no_unexpected_errors(page):    console_errors = []    page_errors = []    failed_requests = []    server_errors = []    page.on(        "console",        lambda msg: console_errors.append(msg.text)        if msg.type == "error" else None    )    page.on(        "pageerror",        lambda error: page_errors.append(str(error))    )    page.on(        "requestfailed",        lambda request: failed_requests.append(            f"{request.method} {request.url}: "            f"{request.failure}"        )    )    page.on(        "response",        lambda response: server_errors.append(            f"{response.status} {response.url}"        )        if response.status >= 500 else None    )    page.goto("https://test.example.com")    page.get_by_role("link", name="Flights").click()



This strict example assumes the tested flow should have no such errors. In a real application, I would filter known, approved exceptions rather than fail the suite because of unrelated analytics or intentionally aborted requests.
Important distinctions
Event	Meaning
console	Browser console messages, including JavaScript console errors
pageerror	Uncaught JavaScript exceptions on the page
requestfailed	A request failed at the network or browser-request level
response with status 500	An HTTP response was received with a server-error status
A 404 or 500 response is not automatically a requestfailed event: the server may have successfully returned that HTTP response.
Real-world example: A booking confirmation page appears correct, but the browser logs an uncaught JavaScript exception after the payment response. I would fail the relevant test, preserve the diagnostics, and investigate whether the error affects confirmation rendering or subsequent user actions.
Senior-level point: Register listeners before navigation or the action being investigated, or early events may be missed. Also avoid indiscriminately treating every console message as a product defect; define meaningful failure criteria.

10. Your Playwright test suite has become slow and flaky. What steps would you take to optimize it?
Interview answer:
I would measure the suite before making changes. I would separate genuine application defects from test instability and then optimize the biggest sources of wasted time.
My approach would cover test isolation, authentication, synchronization, parallel execution, network dependencies, locator reliability, and reporting.
Step 1: Identify slow and flaky tests
Run the suite with timing and detailed output:
pytest -v --durations=20


This identifies the 20 slowest test calls.
For tests that fail intermittently, use controlled repeat runs or a rerun plugin to quantify the failure rate. I would not treat a passing retry as proof that the test is fixed.
Step 2: Remove unnecessary waits
Avoid:
import timetime.sleep(5)



Prefer:
from playwright.sync_api import expectexpect(    page.get_by_test_id("booking-confirmation")).to_be_visible(timeout=10000)



The assertion waits for the expected condition rather than blindly sleeping.
Step 3: Reuse authentication where appropriate
Authenticate once using an approved setup process and reuse storage state for tests that can safely share the same identity.
This avoids repeating a lengthy SSO flow in every test. Tests that modify shared data should use isolated accounts or worker-specific authentication state.

Step 4: Run independent tests in parallel
For example, divide tests into smoke, regression, and browser-specific groups. Run independent tests in parallel while ensuring that test data, accounts, and output files do not collide.
Parallelism should be increased gradually because excessive concurrency can overload the application or database and create new failures.
Step 5: Mock expensive dependencies selectively
Use deterministic API mocks for frontend-only scenarios, and reserve real backend calls for integration tests. Avoid making every UI test depend on a slow third-party service.
Step 6: Improve test architecture
- Use page objects or reusable fixtures for common workflows.
- Keep each test focused on one business behavior.
- Create and clean up test data predictably.
- Use stable locators.
- Capture traces, screenshots, and logs on failure.
- Remove redundant tests that provide no additional coverage.
- Keep retries as a diagnostic mechanism, not a substitute for fixing defects.
Example: Reusable fixture with isolated test pages
# conftest.pyimport pytestfrom playwright.sync_api import sync_playwright@pytest.fixturedef page():    with sync_playwright() as p:        browser = p.chromium.launch(headless=True)        context = browser.new_context()        page = context.new_page()        yield page        context.close()        browser.close()



This provides a fresh browser context for each test using the fixture, preventing cookies and local storage from leaking between tests. For larger suites, I would use a more optimized shared-browser fixture while retaining per-test context isolation.
Example: Parallel execution
Install pytest-xdist:
pip install pytest-xdist


Execute tests using four workers:
pytest -n 4


I would first verify that the tests are independent and that the environment can support four concurrent workers.
How I would measure improvement
Metric	What I would monitor
Total execution time	Whether the suite finishes faster
Flaky-test rate	How often tests fail intermittently
Retry rate	Whether failures are being masked by retries
Failure diagnosis time	How quickly the root cause can be identified
Coverage	Whether critical business flows remain tested
Real-world example: An airline regression suite takes 45 minutes and frequently fails on flight search. I discover that many tests repeat SSO login, rely on fixed sleeps, and use the same booking account. I would reuse safe authentication state, replace sleeps with condition-based assertions, isolate booking data, and parallelize independent tests. I would compare execution time and flaky-test rate before and after the changes.
Senior-level point: My goal is not merely to make the suite faster. It is to make it faster, deterministic, diagnosable, and trustworthy.

Part 1 — Basic Playwright Interview Questions
2. What are the advantages of Playwright?
Answer: Playwright is a modern browser automation framework that offers reliable, cross-browser testing with built-in synchronization and powerful debugging tools.
Key advantages:
1. Auto-waiting: Waits for elements to become actionable before performing supported actions.
2. Cross-browser support: Chromium, Firefox, and WebKit.
3. Multiple languages: JavaScript, TypeScript, Python, Java, and .NET.
4. Fast execution: Supports parallel testing and efficient browser contexts.
5. Network interception: Can mock APIs, inspect requests, and simulate failures.
6. Multiple tabs: Supports popups, multiple pages, and browser contexts.
7. Debugging: Offers traces, screenshots, videos, and Inspector tools.
8. Authentication reuse: Can save and restore browser storage state.
9. Modern web support: Handles SPAs, dynamic content, and asynchronous interfaces.
10. CI/CD integration: Works with common pipeline systems.
Real-world example: For an airline application, I can search flights, intercept a pricing API, validate a booking confirmation, and run the same tests across Chromium, Firefox, and WebKit.
3. What are the disadvantages of Playwright?
Answer: Although Playwright is powerful, it has limitations that need to be considered when designing an automation framework.
- Learning curve: Modern locator strategies, contexts, fixtures, and asynchronous behavior require practice.
- Legacy-browser limitations: It does not provide the same breadth of legacy browser support as some Selenium-based setups.
- Real-device limitations: Browser emulation does not replace physical-device testing.
- Third-party authentication: SSO and MFA flows may require special test-environment configuration.
- Test maintenance: Poor selectors and tightly coupled tests can still be flaky.
- Language-specific differences: The official test runner is designed for JavaScript/TypeScript; Python users commonly use pytest.
- Environment setup: Browser binaries and Linux dependencies must be installed correctly in CI.
- Application-specific constraints: Captchas, hardware-dependent workflows, and native application interactions may require other tools or dedicated test hooks.
